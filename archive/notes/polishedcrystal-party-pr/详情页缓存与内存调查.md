# 详情页缓存与内存调查

> 2026-09-28复核：本文是PR19修复前诊断。当前源码已通过ZhSummaryMarkWindow扫描详情窗口活引用，并在详情显示期间跳过普通tilemap上传；PR19已合并。下文“不是修复完成”“下一步”仅指当时阶段。真实最坏活key峰值、调用栈峰值及全场景生命周期仍未全面验证，历史损坏槽数不能证明容量足够。当前入口见[新会话交接](新会话交接.md)。

范围：PR18基线与当前详情页极限测试ROM；不把损坏后的缓存记录当正确需求峰值。证据 /Users/zhaoc/source/summary-memory-audit/。布局工作暂停，未扩大任何资源。

## 分配量

链接map对比：详情页改动前后，ZH bounded text state均81B；ZH glyph cache均495B；ZH temporary map keys均1800B；Window Stack均4096B。详情页没有新静态WRAM分配。这三块中文专用内存合计2376B，是已有汉化框架相对英文版本的成本，不能说汉化完全没有额外内存。调用栈瞬时峰值尚未测量。

原版详情窗口wSummaryScreenWindowBuffer为320B，调色板64B、OAM影子160B、扫描线表32B均原有；两次HDMA各19×16=304B（tile和attr）是搬运量，不是额外分配。

VRAM缓存候选每bank为$80..$D5，共86个8×8 tile=43个8×16块，1376B；普通双bank共2752B候选，bank0跳过$BC/$BD后可用2720B。当前详情页只允许bank1，容量43块/1376B，没有扩池。相比原版静态单字节字库，新中文需要更多动态组合图块；五个12px汉字需8个8×16块（256B）而非五个8×8字格。共享/重复组合可复用，不能把各元素矩形相加当物理需求。

## 已证实错误

1. 缓存满时ZhEnsureCacheBlock调用普通ApplyAttrAndTilemapInVBlank，设置hBGMapMode并等待帧。详情页有自己的window/HDMA/扫描线流程，不能插入普通页面刷新。隔离禁用这次上传后大范围立绘/调色板/边框破坏消失，文字错误仍存在。不是修复完成。
2. ZhGlyphCacheRecover只扫描wTilemap/wAttrmap，没有扫描320B详情窗口。极限首次粉页读取bank1引用：普通图18块，窗口24块，去重并集41块，其中23个窗口引用不在普通图内，且23个未被used表标记。蓝页普通图21块、窗口0个bank1块；返回粉页普通图18、窗口24、并集39，20个窗口引用未标记。bank0静态英文字符已排除，避免把原字体误算为中文缓存。
3. 上述是绘制结束后的物理槽引用，已经可能被错误复用，不能证明所需独立key只有41块，也不能证明43块一定足够。必须在分配/回收发生前记录目标key、全部存活引用及峰值后再下结论。
4. 当前清缓存发生在旧页面退出显示之前；新旧页面同时存活、立绘动画及硬件图块保留也要核对。

## 下一步（不扩容）

补齐详情window引用扫描；详情页不走普通地图上传；定义旧页退场、新页构建、提交切换的生命周期；在缓存满事件记录全部活key和峰值。优先避免页面过渡同时保留两套文本，再评估真正容量。不因当前乱码直接申请扩池。ROM字库/索引占用另计，不与WRAM/VRAM混算。

测量方式：每个阶段独立从同一存档重放，结束后才切WRAM bank读取，随后退出，不把调试bank变化带入下一阶段。原存档SHA不变。
